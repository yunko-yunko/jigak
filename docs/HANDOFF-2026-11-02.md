## 3. Cloud Run 설정과 이유

`MOBILITY_SIMULATION`에 `scooter` 또는 `ebike`가 있으면 `deploy/cloud-run.ps1`이 아래 설정을 자동으로 붙입니다.

| 설정          | 값                                                       | 이유                                                                                                                                  |
| ------------- | -------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------- |
| CPU / 메모리  | `--cpu 2 --memory 2Gi` (꺼짐: 1 / 512Mi)                 | 실규모 창을 계산할 때 작업자 스레드가 약 550 MB, 서버 전체가 0.8–1.1 GB입니다(추정, 미검증). 작업자와 요청이 CPU를 하나씩 씁니다.     |
| CPU 할당      | `--no-cpu-throttling --cpu-boost`                        | 창 계산은 요청 밖(시작 시, 매일 05:00 KST)에서 돕니다. 요청 기반 CPU에서는 거의 진행되지 않습니다.                                    |
| 최소 인스턴스 | `--min-instances 1` (`-MinInstances -1` = 자동)          | 첫 창 계산에 약 50–90초가 걸립니다(미검증). 상시 1대 비용은 하루 약 3–4달러로 추정합니다.                                             |
| startup probe | `GET /api/health/ready`, 5초 간격, 실패 60회(최대 300초) | 창이 준비되기 전에는 트래픽을 받지 않게 합니다. 시뮬레이터가 꺼져도 붙습니다.                                                         |
| 창 저장 볼륨  | `-SimulationWindowBucket <버킷>` → `/sim-windows`        | 재시작하거나 새 인스턴스가 떠도 약 0.1초에 읽습니다(하루 약 21 MB, zstd). 버킷은 서울 리전의 비공개 버킷이고, 7일 lifecycle을 둡니다. |
| 최대 인스턴스 | 창 버킷이 없으면 `-MaxInstances 2` 이하                  | 버킷이 없으면 새 인스턴스마다 창을 다시 계산합니다.                                                                                   |

창 버킷을 만드는 명령은 [DEPLOYMENT.md](DEPLOYMENT.md)의 "시연용 가상 킥보드·전기자전거" 절에 있습니다.

수동 대체의 모델 업로드와 볼륨 연결(처음 한 번만 합니다. 이후 `gcloud run deploy`는 이 볼륨을 그대로 둡니다):

```bash
cd <압축 푼 모델 폴더>
shasum -a 256 -c SHA256SUMS.txt          # 5개 모두 OK인지 확인
gcloud storage buckets create gs://<프로젝트>-models --location=asia-northeast3 \
  --uniform-bucket-level-access --public-access-prevention
gcloud storage cp public-bus-operational.json spatial-bus-operational.json rail-gate-operational.json \
  spatial-bicycle-operational.json bicycle-ride-times-202606.json gs://<프로젝트>-models/
gcloud storage buckets add-iam-policy-binding gs://<프로젝트>-models \
  --member=serviceAccount:<런타임 서비스 계정> --role=roles/storage.objectViewer
gcloud run services update perception-map --region asia-northeast3 \
  --add-volume name=models,type=cloud-storage,bucket=<프로젝트>-models,readonly=true \
  --add-volume-mount volume=models,mount-path=/models
```

서버는 30초마다 모델 파일의 수정 시각을 확인합니다. 그래서 버킷의 파일만 바꿔도 재배포 없이 새 모델을 읽습니다(`bicycle-ride-times`와 공휴일 달력만 시작할 때 한 번 읽습니다).

### 지도 타일과 NGII 규칙

NGII 지도는 **앱 서버를 거쳐서만** 제공합니다(사용자 결정, 11-02). 버킷은 비공개이고, 서비스가 `/maps`로 붙여 `GET /api/maps/seoul-ngii-v1.pmtiles`에서 Range 요청으로만 내려줍니다.

```bash
# NGII 전용: 서울 리전 비공개 버킷, 국외 반출 금지
gcloud storage buckets create gs://<프로젝트>-ngii-kr --location=asia-northeast3 \
  --uniform-bucket-level-access --public-access-prevention
gcloud storage cp seoul-ngii-v1.pmtiles gs://<프로젝트>-ngii-kr/
# 런타임 서비스 계정만 읽습니다. allUsers 권한과 버킷 CORS는 넣지 않습니다.
gcloud storage buckets add-iam-policy-binding gs://<프로젝트>-ngii-kr \
  --member=serviceAccount:<런타임 서비스 계정> --role=roles/storage.objectViewer

# OSM 상세 지도는 지금처럼 공개 버킷에 둡니다.
gcloud storage cp korea-detail-v1.pmtiles gs://jigak-bucket1/
```

- env yaml에 `MAP_NGII_PMTILES_PATH: '/maps/seoul-ngii-v1.pmtiles'`를 넣고 `cloud-run.ps1`에 `-MapBucket '<프로젝트>-ngii-kr'`를 더합니다(읽기 전용 볼륨 `name=maps`). PowerShell 없이 붙이는 명령은 SERVER-GUIDE 3절에 있습니다.
- 서버는 한 번에 한 구간, 512 KiB까지만 줍니다. Range가 없으면 400이고 파일 전체를 주지 않습니다. IP마다 분당 600회 제한이 있고, 응답은 `Cache-Control: private, max-age=300`입니다.
- 브라우저 출처는 `CORS_ORIGINS`와 지도 프레임의 `Origin: null`만 받습니다. 쿠키는 받지 않습니다.
- NGII 자료는 공개 버킷, Cloud CDN, 다른 리전, 멀티 리전 버킷에 두지 않습니다. 출처 표기 `© 국토지리정보원 수치지형도`는 앱에 이미 있습니다.
- 앱 빌드 환경변수는 사용자에게 전달합니다(서버 변수가 아닙니다):
  - `EXPO_PUBLIC_MAP_DETAIL_TILES_URL=https://storage.googleapis.com/jigak-bucket1/korea-detail-v1.pmtiles`
  - `EXPO_PUBLIC_MAP_NGII_TILES_URL=https://<API 도메인>/api/maps/seoul-ngii-v1.pmtiles`

## 5. 모델 자동 갱신

서울 버킷의 Cloud Run Job이 하루 세 번(05:30, 09:30, 13:30 KST) 모델을 다시 학습·평가·승격하고, 서비스는 `manifest.json`을 따라 재시작 없이 바꿉니다. 설치와 첫 세대 만들기, 확인, 롤백은 [SERVER-GUIDE-2026-11-02.md](SERVER-GUIDE-2026-11-02.md) 4절에 순서대로 적었습니다. 동작 규칙은 [MODEL-REFRESH.md](MODEL-REFRESH.md)입니다.

- 첫 manifest(세대 1)를 만드는 번들은 사용자가 준 `dist/handoff-20261102/model-store-bootstrap`입니다. 버킷의 `bootstrap/`으로 올리고 Job을 `init --from-bundle`로 한 번 실행합니다.
- Job 코드는 백엔드 저장소의 `model-refresh/`에 있습니다(러너, 학습기, `Dockerfile`, `cloudbuild.yaml`, 고정 입력 `data-static/`, 테스트). 백엔드만 담은 저장소로 이미지를 만들 수 있고, 설치 스크립트는 그 루트에서 `bash deploy/model-refresh-job.sh …`입니다. 번들만 사용자 PC(모노레포)에서 받아 `--bundle <폴더>`로 넘깁니다(SERVER-GUIDE 4-2).
- 백엔드 저장소로 옮길 때는 `model-refresh/` 폴더 전체와 `.gitattributes`를 함께 올립니다. 새로 생긴 파일(`scripts/holiday-env.ts`, `scripts/model-refresh/incumbent-gate.py`, `tsconfig.json`, `cloudbuild.trigger.yaml`, `data-static/*`, `data/.gitkeep`, `tests/jobLayout.test.ts`, `tests/trainerParity.test.ts`, `tests/helpers/`, `tests/fixtures/`)이 빠지면 학습 단계가 `./holiday-env`를 못 찾고 이미지 빌드가 멈춥니다. 같은 커밋에 `package.json`, `.gitignore`, `.gcloudignore`, `.prettierignore`, `deploy/model-refresh-job.sh`도 넣습니다.
- `main` 푸시는 API만 배포합니다. Job 이미지를 푸시마다 바꾸려면 `model-refresh/cloudbuild.trigger.yaml` 트리거를 따로 만들고 기존 API 트리거에는 `ignoredFiles: model-refresh/**`를 둡니다(MODEL-REFRESH.md "이미지 자동 빌드").
- 자동 갱신을 쓰지 않을 때는 위 만료 시각 전에 새 모델 파일을 `gs://<프로젝트>-models/`에 같은 이름으로 덮어씁니다(SERVER-GUIDE 4-4). 이 경우 11/07 00:40 이후는 보장되지 않습니다.
- 자동 갱신의 재검증도 지금 공간 버스·지하철 파일을 11/07 20:00(파일 안 공휴일 달력 끝의 4시간 앞) 넘어 늘리지 못합니다. 11/07 00:40 전에 새 학습이 승격돼야 하고, Job이 매 실행 그것을 시도합니다.
- 만료된 모델은 서버가 쓰지 않고 공급자 시간으로 돌아갑니다. 서버가 멈추지는 않습니다.

## 6. 배포 순서

1. **코드:** `git pull origin dev`를 받고 아래 데이터 파일이 있는지 확인합니다. 새로 추가된 파일이라 빠지면 기능이 꺼집니다. 이미지에 넣는 일은 `npm run build`의 `copy-assets.mjs`가 합니다.
   ```bash
   cd jigak-backend
   ls src/common/engine/realtime/data/shared-mobility-{return-rules,door-points,demand,foot-weights}-v1.json \
      src/common/engine/realtime/data/seoul-pm-parking-rules-v1.json \
      src/common/engine/connectivity/data/seoul-subway-exits-v1.json \
      src/modules/places/data/place-stations-v1.json
   npm ci && npm run build && npm test
   ```
2. **비밀:** 예비 키 3개를 Secret Manager에 새 비밀로 만듭니다(값은 표준 입력으로 넣어 셸 기록에 남기지 않습니다).
   ```bash
   gcloud secrets create jigakmap-kakao-rest-key-spare --replication-policy=user-managed --locations=asia-northeast3
   gcloud secrets versions add jigakmap-kakao-rest-key-spare --data-file=-   # 값을 붙여 넣고 Ctrl-D
   # jigakmap-data-go-kr-key-spare, jigakmap-seoul-open-api-key-spare 도 같은 방식으로 만듭니다.
   gcloud secrets add-iam-policy-binding <비밀> --member=serviceAccount:<런타임 서비스 계정> --role=roles/secretmanager.secretAccessor
   ```
3. **버킷:** 창 저장 버킷(DEPLOYMENT.md 명령)과 비공개 NGII 버킷을 만들고 파일을 올립니다(§4). 모델 버킷 `<프로젝트>-jigak-models`는 5번의 Job 설치 스크립트가 만듭니다.
4. **env yaml:** `cp deploy/cloud-run.env.example.yaml deploy/cloud-run.env.yaml`로 만들고(이 파일은 git에 없습니다) `REPLACE_*` 값을 모두 채운 뒤 다음 값을 넣습니다: `MOBILITY_SIMULATION: 'scooter,ebike'`, `MOBILITY_SIMULATION_WINDOW_DIR: '/sim-windows'`, `DATA_GO_KR_DAILY_LIMIT: '1000'`, `MODEL_MANIFEST_PATH: '/models/manifest.json'`(SERVER-GUIDE 2-3), `MAP_NGII_PMTILES_PATH: '/maps/seoul-ngii-v1.pmtiles'`, 필요하면 OSRM URL. 모델 경로 5개(`ETA_*_PATH`, `BICYCLE_RIDE_TIMES_PATH`)는 비워 둡니다.
5. **모델(배포 전에):** [SERVER-GUIDE-2026-11-02.md](SERVER-GUIDE-2026-11-02.md) 4절이 유일한 기준입니다. 4-2 Job·Scheduler 설치(버킷 `<프로젝트>-jigak-models`를 만듦) → 4-1 번들 업로드와 `init --from-bundle` 순서로 합니다. 이 단계를 건너뛰면 자동 갱신이 없어 모델이 파일 만료(11/05, 11/07)에 그대로 끝납니다.
   - 수동 대체(자동 갱신을 쓸 수 없을 때만): `MODEL_MANIFEST_PATH`를 비우고 4번의 모델 경로 5개를 `/models/<파일>`로 채운 뒤, 7번 배포 뒤 §4의 명령으로 `<프로젝트>-models` 버킷을 `services update --add-volume name=models`로 붙입니다(SERVER-GUIDE 4-4). 이때는 6·7번에서 `-ModelBucket`을 빼고, 새 모델이 생기지 않으므로 11/07 00:40 이후는 보장되지 않습니다.
6. **계획 확인:** PowerShell에서 실행합니다. `cloud-run.ps1`은 `MODEL_MANIFEST_PATH`와 `-ModelBucket`이 짝이 맞지 않으면 멈춥니다.
   ```powershell
   $deployment = @{
     ProjectId = '<프로젝트>'; Region = 'asia-northeast3'; Service = 'perception-map'
     ArtifactRepository = '<저장소>'; ImageTag = 'release-20261102-1'
     InstanceConnectionName = '<프로젝트>:asia-northeast3:<SQL 인스턴스>'
     ServiceAccount = '<런타임 서비스 계정>'
     DbPasswordSecret = '<비밀>:<버전>'; AuthEncryptionKeySecret = '<비밀>:<버전>'
     SecretBindings = @{
       KAKAO_REST_API_KEY = '<비밀>:<버전>'
       KAKAO_REST_API_KEY_FALLBACK = 'jigakmap-kakao-rest-key-spare:1'
       DATA_GO_KR_SERVICE_KEY = '<비밀>:<버전>'
       DATA_GO_KR_SERVICE_KEY_FALLBACK = 'jigakmap-data-go-kr-key-spare:1'
       SEOUL_OPEN_API_KEY = '<비밀>:<버전>'
       SEOUL_OPEN_API_KEY_FALLBACK = 'jigakmap-seoul-open-api-key-spare:1'
       # 주의: 스크립트가 --set-secrets로 비밀 전체를 교체합니다. 지금 서비스에 붙은 기존 비밀
       # (SEOUL_BIKE_API_KEY, SEOUL_CITY_DATA_API_KEY, TRAFFIC_SIGNAL_API_KEY 등)도 모두 다시 적어야 합니다.
       # 값은 반드시 이름:숫자버전 형식이고 latest는 안 됩니다.
     }
     MaxInstances = 2; MinInstances = -1
     SimulationWindowBucket = '<프로젝트>-sim-windows'
   ```

   계획에 `--cpu 2 --memory 2Gi --min-instances 1 --no-cpu-throttling --cpu-boost --startup-probe ... --add-volume name=sim-windows`와 모델 볼륨 `name=models`(`<프로젝트>-jigak-models`, 읽기 전용, `/models`), 지도 볼륨 `name=maps`(`<프로젝트>-ngii-kr`, 읽기 전용, `/maps`)가 있는지 확인합니다(SERVER-GUIDE 4-3).
7. **배포:** `-PlanOnly`를 빼고 실행합니다. 빌드, migration Job, 서비스 배포 순으로 진행합니다.
8. **확인:** §7의 점검과 SERVER-GUIDE 4-3의 `modelRefresh` 확인을 합니다. 이상이 없으면 사용자에게 앱 빌드를 요청합니다(§8).

> 미검증: `--add-volume name=sim-windows`를 매 배포마다 다시 붙일 때 gcloud가 "이미 있음" 오류를 낼 수 있습니다. 오류가 나면 그 리비전 배포 명령에 `--clear-volumes --clear-volume-mounts`를 앞에 두고 `models`, `sim-windows`, `maps` 볼륨을 함께 다시 붙입니다.

```bash
API=https://<API 도메인>
```

경로 검색 표본입니다. 결과에 도보·대중교통·킥보드·전기자전거 후보가 나와야 하고, 지하철 단계에는 "N번 출구"가 보여야 합니다.

```bash
NOW=$(($(date +%s)*1000)); DL=$((NOW+3600000))
P='"preferences":{"allowRunning":false,"allowBicycle":true,"maxRunningMeters":0,"maxBicycleMeters":5000,"runningPace":"steady","preparationSeconds":0,"bicycleReady":false,"allowTaxi":true,"allowScooter":true,"allowEbike":true,"hasScooterLicense":true}'
route() { curl -s -X POST $API/api/routes/search -H 'content-type: application/json' -d "{\"origin\":{\"id\":\"a\",\"name\":\"$1\",\"address\":\"\",\"latitude\":$2,\"longitude\":$3},\"destination\":{\"id\":\"b\",\"name\":\"$4\",\"address\":\"\",\"latitude\":$5,\"longitude\":$6},\"deadline\":$DL,\"now\":$NOW,$P}" | jq '[.routes[]? | {title, min: (.durationSeconds.min/60|floor), max: (.durationSeconds.max/60|ceil)}] | .[:6]'; }
route 강남역 37.4979 127.0276 선릉역 37.5045 127.0490
route 서울숲역 37.5436 127.0446 건대입구역 37.5404 127.0702
curl -s "$API/api/places?q=%ED%99%8D%EB%8C%80" | jq '[.places[0:3][] | .name], .provenance.provider'   # 홍대: 역이 1위, 홍익대학교도 목록에 있어야 함
```

응답 필드 이름이 다르면 `jq '.'`로 원문을 봅니다. 마지막 판단은 앱에서 같은 검색을 해 보고 합니다. 앱은 응답을 엄격하게 검증하기 때문에, 원문 JSON이 정상이어도 앱에서 거부될 수 있습니다.

## 8. 호환성: 앱과 서버는 같이 바꿉니다

- 이전 앱 빌드는 새 서버 응답을 거부합니다. 예를 들어 health의 버스 상태 `quota`, 새 이동수단 종류(`ebike`), 지하철 출구 필드가 그렇습니다. 그러면 앱이 "올바른 자료를 보내지 않았어요"를 띄웁니다.
- 순서: 서버 배포 → 점검 통과 → 사용자에게 알림 → 사용자가 같은 커밋으로 앱을 빌드합니다. 심사용 기기에는 새 빌드만 설치합니다.
- 서버를 되돌리면 앱도 그 시점의 빌드로 되돌립니다. DB 마이그레이션은 이번에 추가되지 않았습니다(확인 방법: `src/common/database/migrations` 변경 없음).

### 자체 OSRM (선택)

데이터가 크기 때문에 묶음에 넣지 않았습니다. 두 가지 방법이 있습니다.

1. **복사(권장):** 사용자 Mac의 `mvp/data/osrm/foot-v2`(5.4 GB)와 `mvp/data/osrm/bike`(3.5 GB) 폴더를 외장 디스크나 서울 리전 버킷으로 옮깁니다. 만들 때 쓴 것과 같은 `osrm/osrm-backend` 이미지(v5.26.0)로 띄웁니다. 자세한 절차와 다이제스트는 `OSRM.md`에 있습니다.
2. **다시 빌드:** `bike`와 기본 `foot`은 OSM 파일만 있으면 팀원이 만들 수 있습니다(Docker 필요).
   ```bash
   cd mvp
   mkdir -p data/osrm && curl -L -o data/osrm/south-korea-latest.osm.pbf https://download.geofabrik.de/asia/south-korea-latest.osm.pbf
   sh scripts/build-osrm.sh                          # data/osrm/foot, data/osrm/bike (각 약 2분)
   ```
   `foot-v2`(`scripts/build-osrm-foot-v2.py`, 아파트·학교 안 보행로)는 NGII 지형도(`mvp/data/ngii/gpkg`)가 있어야 해서 **사용자 Mac에서만 다시 만들 수 있습니다.** NGII 자료는 국외 반출 금지라 팀원에게 원본을 주지 않습니다. 팀원이 foot-v2 없이 쓰려면 기본 `foot`을 5001 포트로 띄우고 `PEDESTRIAN_OSRM_URL`에 `http://<호스트>:5001/route/v1/foot`을 넣습니다.

실행 예(서울 리전 VM, RAM 16 GB 이상 권장, 추정). `:latest` 대신 `OSRM.md`에 적힌 다이제스트(`osrm/osrm-backend@sha256:...`)로 고정하세요. 만든 버전과 다르면 파일을 읽지 못합니다:

```bash
docker run -d --name osrm-foot -p 5011:5000 -v $PWD/foot-v2:/data osrm/osrm-backend:latest \
  osrm-routed --algorithm mld --max-table-size 200 /data/korea.osrm
docker run -d --name osrm-bike -p 5002:5000 -v $PWD/bike:/data osrm/osrm-backend:latest \
  osrm-routed --algorithm mld --max-table-size 200 /data/korea.osrm
```

그다음 env yaml에 `PEDESTRIAN_OSRM_URL: 'http://<VM 내부 IP>:5011/route/v1/foot'`, `BICYCLE_OSRM_URL: 'http://<VM 내부 IP>:5002/route/v1/bike'`를 넣습니다. Cloud Run이 VM 내부 IP에 닿으려면 Direct VPC egress가 필요합니다(`cloud-run.ps1`에는 없으므로 `gcloud run services update --network ... --subnet ... --vpc-egress private-ranges-only`). 이 구성은 아직 해 보지 않았습니다(미검증).
